# Chart Analyzer: design

How the service is built and why. Diagram: [architecture.png](architecture.png).

## Flow of one analysis

1. `POST /api/v1/analyses` (image, language, `x-user-id`, optional `Idempotency-Key`).
   The API validates the file, checks the quota, stores the image and, **in one
   transaction**, inserts the analysis (`queued`) and an outbox row. It answers `202`
   with the analysis id.
2. The **outbox relay** (in the worker process) publishes unsent outbox rows to RabbitMQ
   and marks them sent.
3. A **worker** takes the task, claims the analysis and runs the pipeline:
   recognize (AI, cheap) → market data (Finnhub) → full analysis (AI) → validate → save.
   Each step saves a checkpoint; each stage is published as a progress event.
4. The client follows `GET /api/v1/analyses/{id}/events` (SSE) and receives stages, then
   the final result or error. The result is also available via `GET /api/v1/analyses/{id}`.

## Layers

```
src/chart_analyzer/
  domain/          pure rules and value objects; no I/O, no framework
  application/     use cases + ports (interfaces in application/ports)
  infrastructure/  adapters implementing the ports (Postgres, RabbitMQ, Redis, Finnhub, OpenAI, disk)
  api/             FastAPI: routers, schemas, error mapping, SSE
  worker/          process entry point: task consumer + outbox relay
  bootstrap.py     composition root: the only place that wires adapters to use cases
```

Dependencies point inwards: `api`/`worker`/`infrastructure` → `application` → `domain`.
Use cases receive ports through their constructors, so every one is unit-tested with the
in-memory fakes in `tests/fakes.py`.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| Execution | Queue + separate worker, not inside the HTTP request | An analysis takes 8–20 s; it must survive a dropped connection, an API restart and bursts of load |
| API → queue | Transactional outbox | A stored analysis can never be left without a task: both rows commit together |
| Delivery | At-least-once + idempotent worker | `claim` is one atomic `UPDATE`; duplicates of a finished analysis are dropped |
| Checkpoints | Recognition and market snapshot saved as JSONB after each step | A retry resumes where it stopped instead of paying for the same AI call twice |
| Retries | Delay queues (5 s / 30 s / 120 s), then DLQ | Transient provider errors heal by themselves; a poisoned task must not loop forever |
| Order of steps | Cheap recognition → market data → expensive analysis | If the ticker is unreadable or Finnhub is down we stop before the expensive call |
| Result | Complete or failed, never partial | Part 2 requires the market blocks to be populated with real data |
| Quota | Count only successful analyses; reserve an upper bound per active analysis | "Up to 500,000" is a hard cap, yet the cost is known only after the AI answers |
| Quota concurrency | `pg_advisory_xact_lock` per user around check + insert | There is no per-user row to `SELECT … FOR UPDATE`; the reservation is derived from statuses and cannot leak |
| Localization | Enums as stable codes; AI free text and error messages in the user's language | The client keys colours/icons on codes and translates labels itself |
| Market data | Finnhub behind `MarketDataProvider`, cached in Redis | Free tier allows 60 requests/minute for all users together |
| Images | Files on a volume behind `ImageStorage` | Swappable for S3 without touching use cases |
| Users | No table; `user_id` is an opaque string from `x-user-id` | Users live in another service; the assignment says auth is already handled |

## Data model (PostgreSQL)

`analyses`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid PK | generated by the API |
| `user_id` | varchar(128) | from `x-user-id` |
| `idempotency_key` | varchar(128) null | unique together with `user_id` |
| `language` | varchar(8) | `Language` value |
| `status` | varchar(16) | `queued` / `processing` / `completed` / `failed` |
| `stage` | varchar(32) | `queued` / `recognizing` / `market_data` / `analyzing` / `done` |
| `image_key`, `image_content_type` | text, varchar(64) | location in `ImageStorage` |
| `recognition` | jsonb null | checkpoint of step 1 (`ChartRecognition`) |
| `market_snapshot` | jsonb null | checkpoint of step 2 (`MarketSnapshot`) |
| `result` | jsonb null | `AnalysisResult`, set on completion |
| `error_code` | varchar(64) null | `ErrorCode` value, set on failure |
| `tokens_used` | integer | sum of all AI calls of this analysis |
| `attempts` | integer | incremented by every claim |
| `locked_at` | timestamptz null | lease start; a claim older than the lease may be taken over |
| `created_at`, `updated_at`, `completed_at` | timestamptz | `completed_at` is set for both terminal statuses |

Indexes: `(user_id, created_at desc)` for history; partial `(user_id, completed_at)`
where `status = 'completed'` for the quota sum; partial `(user_id)` where status is
active for the reservation count; unique `(user_id, idempotency_key)`.

`outbox`

| Column | Type | Notes |
|---|---|---|
| `id` | bigserial PK | publish order |
| `analysis_id` | uuid | payload of the task |
| `created_at` | timestamptz | |
| `sent_at` | timestamptz null | null = not yet published; partial index on unsent rows |

Quota usage of a user for today = `SUM(tokens_used)` over `completed` analyses with
`completed_at >= 00:00 UTC`, plus the count of active (`queued`/`processing`) analyses.

## RabbitMQ topology

| Object | Purpose |
|---|---|
| exchange `analysis` (direct) | entry point |
| queue `analysis.tasks` (durable), key `tasks` | work queue; dead-letters to `analysis.dlx` |
| queues `analysis.retry.<N>s` (durable), key `retry.<N>` | one per delay; `x-message-ttl = N s`, no consumers, dead-letter back to `analysis` / `tasks` |
| exchange `analysis.dlx` (direct) → queue `analysis.dlq`, key `dead` | tasks that ran out of attempts |

Message body: `{"analysis_id": "<uuid>"}`, persistent. Header `x-attempt` (int, starts
at 1). One queue per delay (instead of per-message TTL) avoids head-of-line blocking.
The consumer uses manual acks: `ack` after handling, `reject(requeue=False)` to dead-letter.

## Redis

| Key | Type | Purpose |
|---|---|---|
| `analysis:{id}:events` | Stream | progress events (`type`, `data` JSON); expires after `PROGRESS_TTL_SECONDS` |
| `market:{kind}:{type}:{symbol}` | String (JSON) | cache of Finnhub answers with per-kind TTL |

A Stream (not pub/sub) so a client that reconnects can replay from its last event id.

## Errors

Every error response is `{"error": {"code": "<ErrorCode>", "message": "<localized>"}}`.
Request errors are HTTP 4xx. Analysis errors are reported through the analysis status
and a final `failed` event, with the message in the analysis' language.

## Known limits

- If a worker dies between the AI's answer and the checkpoint commit, that one step is
  paid for again on retry. The extra spend is not charged to the user's quota.
- A task redelivered right after a worker crash waits for the lease
  (`ANALYSIS_LEASE_SECONDS`) before another worker takes over.
- Rejected uploads (not a chart) cost recognition tokens that the quota does not count,
  per the assignment's wording "successful analyses". In production this needs a
  separate attempts limit; the spend is stored per analysis to make that easy.
- Finnhub's free tier has no analyst price targets, and its company news covers North
  American companies only.
